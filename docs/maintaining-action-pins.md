# Maintaining GitHub Actions pins (resolve, never predict)

depfence pins every third-party GitHub Action to a full 40-character commit SHA.
This is the supply-chain control that stops a hijacked tag (`@v4`) from silently
shipping malicious code into CI.

A pin is only trustworthy if the SHA is **real**. A SHA written from memory — or
generated by an AI assistant — can look perfect (40 hex chars, a tidy `# v4`
comment) and still point to no commit that ever existed. So the rule is:

> **Never type or guess an action SHA. Resolve it with a tool, then verify it.**

## Pinning / updating actions

Use [`ratchet`](https://github.com/sethvargo/ratchet) — it reads the `# vX` comment,
resolves the tag against the network, and writes back the real commit SHA.

```bash
# Pin all unpinned refs in a workflow
ratchet pin .github/workflows/ci.yml

# Re-resolve an existing (possibly wrong) pin from its # vX comment
ratchet unpin .github/workflows/ci.yml && ratchet pin .github/workflows/ci.yml

# Bump pinned actions to the latest release of the same major
ratchet upgrade .github/workflows/ci.yml
```

## Verifying pins

depfence does this natively now: the `resolve_existence` scanner resolves every
SHA-pinned action against GitHub during a normal `depfence scan` (online) and reports
any pin that points to no real commit as a CRITICAL `fabricated_reference`. Set
`GITHUB_TOKEN` for the 5000 req/hr limit; disable with `DEPFENCE_RESOLVE_EXISTENCE=0`.

`scripts/verify-action-pins.sh` is the standalone, dependency-free equivalent — it asks
the GitHub API whether each pinned SHA is a real commit and fails on any that is not. It
runs in CI (the `action-pins` job in `ci.yml`) as an independent cross-check, and can be
run locally:

```bash
gh auth login            # one-time
scripts/verify-action-pins.sh                 # checks .github/workflows
scripts/verify-action-pins.sh path/to/repo    # checks another tree
```

## Auditing for other workflow risks

Use [`zizmor`](https://github.com/zizmorcore/zizmor) for expression injection,
credential persistence, over-broad `permissions:`, and cache poisoning:

```bash
zizmor .github/workflows/
```

## Checklist for any workflow change

1. `ratchet pin` (or `upgrade`) — never hand-write a SHA.
2. `scripts/verify-action-pins.sh` — every pin resolves to a real commit.
3. `zizmor .github/workflows/` — no new injection / permission findings.
4. Each workflow has a least-privilege top-level `permissions:` block; jobs escalate
   only what they need.
